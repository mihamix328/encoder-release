# Encoder

**Клиент-серверное приложение для шифрования файлов с отдельным устройством обработки и панелью администратора.**

Пользователь работает в приложении на Windows или macOS, а криптографические операции выполняет Linux-сервер. Компоненты связаны по TLS. Сервер может работать на отдельной плате: приложения на компьютере дают удобный интерфейс, устройство обрабатывает запросы и хранит серверные данные.

Этот репозиторий, **encoder-release**, содержит актуальную линию выпуска проекта. Старые encoder и encoder-next не следует использовать вместо него при установке или продолжении разработки. Готовые приложения находятся в [Releases](https://github.com/mihamix328/encoder-release/releases).

## Для чего и для кого

Encoder создаётся прежде всего для небольших компаний, которым нужен дополнительный инструмент защиты рабочих файлов: договоров, внутренних документов и другой конфиденциальной информации. Цель проекта — сделать шифрование доступным через понятное приложение, вынести обработку на отдельное устройство в локальной сети и дать администратору возможность управлять доступом сотрудников к операциям.

- **Сотрудник компании** работает с файлами на своём компьютере, подключается к устройству под индивидуальной учётной записью и выполняет разрешённые операции шифрования и расшифрования.
- **Администратор** создаёт пользователей, сбрасывает пароли, блокирует учётные записи, задаёт разрешения на операции и просматривает состояние устройства.

Пример применения — небольшой офис, где несколько сотрудников используют общий сервер шифрования, а администратор централизованно управляет их учётными записями и разрешениями. Защита рабочих документов помогает снижать риск раскрытия информации, потери доверия клиентов и связанных с утечками убытков. Дополнительно Encoder можно использовать для личных файлов и учебных демонстраций.

Это целевое назначение проекта, а не заявление о промышленном внедрении или завершённом аудите безопасности. Encoder является дополнительным инструментом защиты: его использование само по себе не гарантирует соблюдения всех требований законодательства. Текущие разрешения относятся к операциям шифрования и расшифрования; права на отдельные документы ещё не реализованы.

## Как работает система

1. Клиент устанавливает TLS-соединение с сервером и проверяет его сертификат.
2. Пользователь входит в учётную запись и выбирает файл.
3. Сервер проверяет разрешение на операцию и выполняет шифрование либо расшифрование.
4. Результат возвращается клиенту. При шифровании текущий клиент заменяет выбранный файл зашифрованным контейнером, поэтому для первого запуска нужна отдельная копия.
5. При серверном хранении ключей для восстановления нужны серверные данные: резервировать следует всю базу, а не только список пользователей.

Сам зашифрованный документ остаётся у пользователя; серверный компонент не следует путать с облачным диском. Запрет дальнейших операций не уничтожает уже полученные пользователем открытые копии.

## Из чего состоит проект

| Компонент | Что делает |
| --- | --- |
| `client/` | Обычный графический клиент: подключение, вход, выбор файлов, выполнение операций |
| `admin/` | Графическая панель: пользователи, разрешения, устройства и сетевое состояние |
| `server/` | Linux-сервер: запросы клиентов, криптографическая обработка и административный API |
| `common/` | Общие библиотеки протокола, TLS, криптографии и служебных функций |
| `deploy/` | Материалы развёртывания и экспериментальной настройки сети |
| `cmake/`, `.github/workflows/` | Сборка, упаковка и автоматизированные проверки |
| `docs/` | Инструкции подключения, сборки, установки и описание ограничений |

## Платформы и возможности

В выпуске v0.1.0-rc.3 доступны обычный клиент и админ-панель для **Windows x64** и **macOS ARM64 (Apple silicon)**, а также кандидат серверного комплекта для **Linux ARM64**. Наличие готовой сборки не заменяет проверку на конкретном устройстве; клиент для Intel Mac этим выпуском не заявляется.

Есть управление учётными записями, отдельные разрешения на шифрование и расшифрование, работа через Ethernet, просмотр состояния сети и поиск Wi-Fi. Изменение Wi-Fi остаётся экспериментальным и по умолчанию отключено. Разрешения на операции не равнозначны отдельным правам на каждый документ или совместному редактированию.

Криптографические операции используют OpenSSL; для нативных Магмы и Кузнечика в режиме MGM требуется сборка с libakrypt. Без этой зависимости сервер отказывает в соответствующих ГОСТ-операциях. Старое обозначение «Стрибог», которое было псевдонимом SHA-256, удалено из новых вариантов; правила совместимости описаны в [GOST_NATIVE.md](docs/GOST_NATIVE.md).

Проект остаётся кандидатом на выпуск. Защита работающей ОС, безопасность хранения ключей, резервирование и доступ к открытым копиям требуют отдельного внимания. Нельзя переносить результаты испытаний из другого репозитория на эту версию без повторного прогона.

## Быстрый запуск

1. Распакуйте готовый архив обычного клиента или админ-панели полностью.
2. Получите у администратора адрес сервера и его публичный сертификат.
3. Откройте `encoder-client.exe`, укажите порт 7443 и свою учётную запись.
4. Для админ-панели используется `encoder-admin.exe`, порт 7444 и отдельный токен.

Ethernet достаточен: Wi-Fi и доступ в Интернет для шифрования не требуются.
ПК и сервер должны иметь доступ друг к другу. Прямой кабель требует настройки
адресов одной подсети; адреса по умолчанию не назначаются клиентом автоматически.
Проверка сертификата должна оставаться включённой.

**Перед шифрованием сделайте копию файла: клиент заменяет выбранный файл
зашифрованным контейнером.** Сначала проверьте полный цикл на несекретной копии.
При серверном хранении ключей нужны резервные копии всей базы сервера.

## Статус выпуска

Это кандидат на выпуск, не заявление о сертификации защиты. Основное шифрование
проверено на устройстве, в том числе после перезагрузки. Финальная проверка
последнего ZIP на чистом втором ПК ещё требуется.
Смена Wi-Fi экспериментальна: не включена в стандартной конфигурации.
Успешное подключение ко второй сети с подтверждением и возврат по истечении
срока подтверждения ещё требуют аппаратной приёмки.

параметра сборки; без него сервер отказывает в ГОСТ-операциях.
